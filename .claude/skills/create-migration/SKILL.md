# Create a Migration

Every schema change goes through a new Alembic migration. Committed migrations are
immutable.

## Steps

1. **Confirm it is a schema change.** Any table/column/index/constraint change
   requires a migration. Data-only changes are separate and reviewed.
2. **Generate a new revision.** Create a fresh Alembic revision (autogenerate as a
   starting point, then review by hand). **Never edit a migration that is already
   committed/merged** — add a new one instead.
3. **For tenant-owned tables, include all of:**
   - `tenant_id UUID NOT NULL`
   - `UUID` primary key (server-generated)
   - `timestamptz` columns storing UTC
   - `ENABLE ROW LEVEL SECURITY` on the table
   - an RLS policy filtering by the current tenant setting
   - indexes on `tenant_id` and common foreign keys/filters
4. **Write a real `downgrade()`.** Make the migration reversible; drop policies,
   RLS, indexes, and columns in the correct order.
5. **Review the autogenerated diff.** Confirm it matches intent; remove spurious
   changes; keep structural and destructive data changes separate.
6. **Test up and down.** Run the migration on a disposable Postgres (Testcontainers)
   both directions. Verify RLS actually isolates tenants.
7. **Do not** run schema changes directly against any database outside the migration.

## Additional Considerations 
Must:

* Review current schema
* Generate a reversible migration
* Add indexes
* verify tenant isolation
* Test upgrade and downgrade
* Never edit previously released migrations

## Definition of Done
New (never edited) revision, reversible, tenant-owned tables have `tenant_id` + RLS
+ policy + indexes, UUID PKs, UTC `timestamptz`, up/down tested.
